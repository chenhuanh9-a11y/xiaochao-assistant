# Qt Quick migration map

Current integrated source status (2026-10-30): the opt-in `client.py` / `Client.qml` client now has home, resource/gallery, settings and help pages, five Qt surfaces, and real resource/settings/info services. `client_live_runtime.LiveRuntime` uses the shared production identity/alignment/core through both mode providers; `client_coordinator.py` connects session commands, pinned reference rendering and authorized aligned rendering. Native capture/global keys remain disabled until the user explicitly binds a window and enables input. The coordinator schedules continuous map refresh every 200ms while its runtime/context guards allow it; this interval is a scheduling setting, not a measured latency guarantee.

The source is still being integrated and is not yet the final committed build input. No Setup build has started. The original `main.py` / `Main.qml` prototype remains available, production Tk entrypoints remain available, and the sibling `qt-lab` trial is unchanged. Candidate confirmation/reselection, candidate cycling, cycle-floor and remaining manual recognition/floor UI parity are unavailable or disabled; custom route editing and online map-package downloads also remain gaps. Do not describe the current client as a complete Tk replacement.

Evidence is bounded: `work/qt-evidence/client-final/client-probe.json` records 18 passing assertions and zero QML warnings for the client's own windows and isolated writes, including stable resources, persisted settings, reference editing and a local update fixture. `work/provider-evidence/live-runtime-synthetic-floor-chain.json` and `live-runtime-refresh-chain.json` exercise real shared providers/core with injected **synthetic frames**; the latter records stable token/pixels/matrix on an unchanged refresh and subsequent refresh/revocation behavior. Both providers prepare (nightmare 26 maps/78 typed layers; difficult 30 declared maps/58 typed layers, with difficult map29's two reliable native-layout bindings explicitly missing). The coordinator reports 89 suite passes with one skip, seven coordinator passes, and no P1/P2 finding in the fresh review; these are source/offline/own-window checks, not native acceptance. These are not native game capture/shortcut acceptance, real-game correctness, or end-to-end performance evidence. The 500ms initial/300ms reopen targets remain unproven.

## Shared runtime boundary

Both nightmare and difficult must use the **same** identity, initial/subsequent alignment, floor transition, front/side entry strategy, job queue/cancellation and commit implementation. Differences belong in resource providers, supported-floor metadata, coordinate contracts and required parameters. Missing entrances/bindings must remain explicit capability gaps. The integrated `LiveRuntime` now adapts the shared production path; further parity work must retain that single owner; importing or constructing `DailyAssistant` as a headless service is not a valid shortcut because it owns Tk variables/widgets, native input, scheduling, capture and display lifecycle.

The Qt boundary should expose immutable snapshots, structured command results and revocable render payloads. `SessionService` already defines injected `snapshot()` / `dispatch(action, payload, cancelled)` and treats operation receipts as distinct from runtime authority; preserve that distinction during integration. Keep the existing `MapIdentityEngine`, `fast_structure_alignment`, `AlignmentCoreV2` / `RoundPose`, `AlignmentPoseTransaction`, `RoundLayerGroup`, `session_state_machine`, resource and transaction services as the computation/validation owners. UI code owns presentation and native-window delivery. A replacement UI must not create a second mode-specific solver or fabricate poses to complete a screen.

## Baseline seam risks (some now implemented; acceptance remains)

1. **Tk/runtime coupling:** production commands frequently read Tk variables and schedule `root.after`. The shared `LiveRuntime`/coordinator now provides the Qt runtime owner; retain one scheduler/command boundary as unsupported controls are completed; do not run two independent owners against a session.
2. **Stale results and revocation:** carry request/frame/open-cycle generation, mode/map/floor, resource identity and display source through worker → commit → Qt pixels. Mode change, close, end round, import and floor change must revoke old payloads immediately; hidden pages must still drain/cancel work.
3. **Three different selections:** resource browsing, preferred/effective author route and locked structural identity are separate. Each rendered floor needs its actual source/bridge; author changes must not silently alter identity, pose or floor. Audit the remaining legacy reset branch.
4. **Native windows and edit state:** preview no-activate/click-through flags are only a starting point. Pinned map, aligned overlay and interactive controls have different focus, hit-testing, coordinate/DPI, visibility and editing contracts. Restore click-through on Finish/Cancel/close/failure.
5. **Resource writer coordination:** live addition/removal, stopped-app upgrades and helper handoff have different capabilities. Preserve receipts, hash-bound confirmation, recovery and writer exclusion; invalidate real image/structure caches and older work after a committed change.
6. **Shortcuts:** one global listener must feed the shared command queue, preserve foreground/text-entry and repeat-edge guards, and shut down deterministically. Keep shortcut recording separate from action dispatch; show actual saved values and elevation/entry diagnostics when implemented.
7. **Settings compatibility and shutdown:** preserve unknown/user data, per-mode choices, geometry and atomic save behavior. The sandbox is currently mandatory. An opt-in production-config bridge needs explicit path policy; never discover/write an installed client implicitly. Drain transaction writers while keeping close outcomes visible.
8. **Acceptance evidence:** historical synthetic replay and source inspection prove neither live authorization nor game timing. Check both modes with representative supported floors/resources, success/failure/cancel/repeat/stale paths, and measure first correct visible pixels separately from solver time (500ms initial / 300ms reopened targets remain unproven).

## Remaining module and acceptance order

1. Complete the unsupported candidate confirm/reselect/cycle and manual floor/recognition controls against the existing single runtime owner; keep unavailable actions disabled until implemented.
2. Complete custom-route editing, remaining control-layout and notice/history parity using existing planning/persistence/services.
3. Finish online map-package operations and verify resource-writer cancellation, receipt-bound removal, upgrade recovery and cache/job invalidation.
4. Validate pinned/aligned native coordinates, DPI/focus, context revocation, author changes and floor transitions with separately authorized real inputs in both modes.
5. Bind final clean source and complete inventory to one private Setup build, then review actual plugin/native notice/source obligations. Installation, game acceptance and publishing remain separate stages.
6. Measure real first-correct-pixel latency, long-run resources and shortcut behavior; source/synthetic success cannot establish those results.
