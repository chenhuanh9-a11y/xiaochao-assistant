# Formal S1 resource and upgrade contract

The 1.0.17 candidate uses source-owned locks for the exact clean source payload,
version bytes, 564 native S1 files across three modes and 325 current S0 base
files. The runtime inventory catalogue is recovery authority; the separate
builder release lock is current build eligibility. Profiles, environment values
and incoming archives cannot enable either policy. The production candidate
purpose grants current-frame candidate display, not private elimination,
durable identity confirmation, live calibration or implicit trace collection.

The published 1.0.7 managed manifest is retained verbatim in the builder lock.
Its current S0 base bytes are unchanged. Published 1.0.3/1.0.4 have 324 unchanged
base entries; published 1.0.5 (8F8B14BD) and 1.0.6 have the same 325 base entries
plus two already registered optional-author metadata paths. The existing narrow
optional-author relinquishment remains unchanged. A candidate omitting or
relocating current base ownership is still rejected before Setup projection.

Published 1.0.2 predates the managed manifest and has 307 verified base files.
Eleven were superseded by later published resource updates. A source-pinned
complete inventory recognizes only all 307 original bytes together, with no
existing managed state. The existing repair transaction then backs up and
replaces the known old files, verifies the entire candidate and commits state.
Missing, changed, linked or partially recognized stock does not grant adoption;
author ownership/dependency constraints, request races and rollback guards still
apply. User settings, custom routes and unrelated files are outside the pin.

S1 author originals remain an optional separate import package. Its 87 original
JPEGs and similarity bridges bind 182 exact Windows native dependencies; the
author catalog never changes recognition resources. B4 remains native-only.
See [the import protocol](s1-author-import-protocol.md) for registration evidence
and limits. Source/offline checks, frozen checks, Setup installation, game
acceptance and publication remain distinct evidence stages.

Inno assigns `{uninstallexe}` during `PerformInstall`, after the installer calls
`inspect`, `prepare` and `start-native`. The unresolved CLI option is omitted.
Pre-native capacity admission keeps that path and its
shortcut target explicitly unknown and reserves space for the later strings;
it does not guess an `uninsNNN.exe` name. Native completion capture and replay
still require the actual owned path and all existing identity checks. See the
upstream [constant expansion](https://github.com/jrsoftware/issrc/blob/main/Projects/Src/Setup.MainFunc.pas)
and [uninstaller filename allocation](https://github.com/jrsoftware/issrc/blob/main/Projects/Src/Setup.Install.pas).
