# 结构包独立更新规划

状态：技术方案草稿。版本阶段、字段名称和示例均供评审，产品与架构分支由人工决定。任务来源见 [Issue #186 第 1 条](https://github.com/chenhuanh9-a11y/xiaochao-assistant/issues/186)。

## 目标与边界

约 3–4 个客户端版本内，让已具备相应能力的正式 Windows 客户端通过导入并启用新版结构包，就能识别新地图、判断楼层、完成首贴和关图重开后的贴合，并显示至少一套与当前结构对齐的底图。验收时固定同一客户端构建，更新前后只改变结构包，且无作者路线也能完成上述流程。首批覆盖的赛季、模式与附加功能由人工确定。

历版已支持的旧结构包继续支持原包导入、已安装版本重启后使用、切换及回退。兼容清单以历版发布、明确交付的制品及其原有功能为准。用户无需重新下载、改包或先删旧包。每个阶段都验证旧包的实际消费者；格式缺失字段与显式不合法值分别处理，继续执行各历史格式原有的完整性、所有权和坐标校验。

沿用 [#171 的 1.1.9 事实报告](structure-pack-only-facts.md)及 [#175 的源码链接修正](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/175)。设计接缝对应报告中的[资源链路](structure-pack-only-facts.md#资源链路入口到最终消费者)和[能力缺口](structure-pack-only-facts.md#逐项能力与缺口)。其中的版本与 PR 状态保留历史基线。本规划采用 #186 的最新项目边界；路线广场导航的缺字段兼容以已合入的 [#163](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/163) 为准，四范围互通 [#134](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/134) 仍是独立草稿。

| 变动 | 客户端与结构包的责任 |
| --- | --- |
| 已支持上下文的新地图或几何修订 | 包交付稳定地图/楼层标识、结构及其 fast 派生、坐标与绑定、适用控件及底图所需数据。客户端负责实际识别、楼层判断、贴合与渲染，仅在这些数据能由已发布能力完整消费时成立。 |
| 新赛季沿用已支持的机制 | 可作为包更新的范围取决于上下文登记方案。赛季/模式身份、采集条件、provider、楼层语义和实际资源需要共同通过验证；显示名本身无准入权限。 |
| 新游戏机制或新运行时能力 | 新采集协议、识别/接受规则、楼层状态机、控件类型、坐标语义及客户端尚无实现的模式，需要先由客户端支持。客户端实现、测试并声明新能力后，资源才可选择依赖它。 |
| 作者图、自定义路线与广场 | 作者路线独立分发，继续按 #168 的逐层结构与坐标绑定选用。图库、广场及安卓网格的可用性按各自能力验证。它们的资产与数据不得改变识别身份、楼层和结构位姿。 |

## 未来 3–4 个客户端版本

以规划获批后启动的下一版计为第 1 版，以下是实施顺序与退出条件，具体版本号由发版列车确定。每阶段保留已支持旧包的回归证据，失败时保留原可用资源和上一阶段承诺。

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| 第 1 版 · 确立旧包兼容 | 以实际发布清单和留存制品核对历史格式、导入状态与 provider。验证旧包原样导入、已安装库直读、Setup 升级保留、重启和资源回退。按第 4 项决策处理仍在兼容范围内却缺 reader/provider 的格式。导出器和导入器对现有契约做正反例往返。 | 困难和噩梦均覆盖发布过的不同包格式和上下文，已有识别、楼层、贴合、底图及可用作者路线行为不退化。缺历史包或缺消费路径单列为未验证/待解决，不能用合成包代替历史发布包。 |
| 第 2 版 · 打通新契约 | 按第 1–3 项决策把清单的声明、上下文登记、能力检查接到导出、导入、启用、provider、页面及会话上下文，和旧读取路径并行。用两模式的实际资源证明数据进入共用链路，并演练不支持新契约、缺依赖、上下文冲突和中断恢复。 | 已部署试验客户端能独立装载旧包和试验包。旧客户端尝试导入新契约时保留原选择与可用资源；缺能力的试验包不进入识别或可选上下文。 |
| 第 3 版 · 用固定客户端验收 | 按第 5–10 项决策确定更新操作、底图、识别数据准入和首批交付方式。用同一构建先运行旧包，再只导入一份包含真实新地图的候选结构包，验证两模式的受影响入口、无作者路线可用、换层、重开及回退后旧图可用。 | 干净 Setup 和带历史资源的升级路径均跑通。真实游戏记录覆盖新地图实际可见结果和现有地图回归；口径内的首批范围可进入资源发布流程。 |
| 第 4 版 · 补齐差额或扩大范围 | 第 3 版有缺口时，集中处理对应的兼容、资源链路或消费路径，重新做固定客户端验收。第 3 版已达标时，只扩大经人工选定且能由已发布能力表达的上下文或交付范围。 | 同一前后对照仍可成立。超出客户端能力的地图随相关客户端功能排期，资源发布说明按已验收范围承诺。 |

## 结构包契约与清单演进

### 版本和字段

现有 `formatVersion` 已区分通用格式 1 与控件银行格式 2，现有 reader 对包、组件和上下文对象执行严格字段校验。扩展布局按第 3 项决策选择；下面定义两个候选布局共同需要表达的语义。基线字段与校验见[事实报告中的格式与客户端能力版本](structure-pack-only-facts.md#逐项能力与缺口)及 [1.1.9 清单源码](https://github.com/chenhuanh9-a11y/xiaochao-assistant/blob/502ec2a9c690a6d0d3e7b25f5cba8b78f51585b5/app/imported_resource_packages.py#L27-L48)。

| 层级 | 继续使用的字段或拟扩展的声明 | 解析和验证 |
| --- | --- | --- |
| 包容器与资源身份 | `schema`、`formatVersion` 区分解析方式。`packageId`、`resourceVersion` 延续包身份与数据版本；版本目录保持不可变，已有 manifest 摘要用于识别实际版本。 | 相同版本及内容可重复导入。相同身份而内容不同视为冲突。发新地图不要求更改客户端版本或数据格式。 |
| 客户端能力 | 复用 `clientCompatibility.resourceProtocol`、`requiredCapabilities`。每个可安装候选声明全部必需的协议与版本化能力。发布索引可镜像这些信息用于筛选，包及实际 provider 校验负责最终判定。 | 客户端提供自己已实现的能力列表。未知必需能力、协议不支持或声明低于实际使用的能力，均在启用前报告具体缺口。UI 不用产品版本号猜能力。 |
| 组件和上下文 | 保留 `components[].type`、`schemaVersion`、`contexts`、`entrypoint`、`dependencies`、`files`。如选用包内声明，候选新增 `contextProfiles` 数组，每项用 `season`、`mode` 关联客户端已实现的 `runtimeProfile` 标识。赛季、模式显示名归显示元数据。 | 单一解析结果服务导出预检、导入、激活、provider 和 UI；每个声明须匹配组件所属上下文，重复或冲突的上下文拒绝启用。包只引用已实现的 profile，声明不能加载代码或指定任意 provider 路径。 |
| 地图和楼层 | 复用基础组件入口的 `runtimeInterfaces` 和其现有索引。已有接口表达不足时，才在有版本的组件语义中补 `mapId`、`floorId`、结构引用与版本键、坐标空间和参考画布、控件绑定及默认底图绑定。 | 身份、结构和楼层索引只保留一处权威定义。地图 ID 在同一赛季和模式内稳定，楼层 ID 在同一地图内稳定，更新时保留已有语义。引用须能在库存和依赖内解析到实际文件、相同上下文和楼层；缺失必需几何、派生数据或坐标绑定不得授予可用性。 |
| 可选能力 | 候选用明确的可选扩展区容纳可跳过的显示元数据。作者路线、导航与图库的绑定沿用相应组件或协议，分别检查实际资产。 | 只忽略在已知格式内明确声明为非必需、且任何必需组件都未引用的数据。未知事实不得默认成通用控件、任意坐标变换或空相似组。 |

解耦以后，`resourceVersion` 跟地图资产发布走，`formatVersion` 跟包解析结构走，组件 `schemaVersion` 跟组件语义走，客户端通过已实现的协议、profile 与能力决定是否可用。需要向用户提示升级时，可显示发布方已验证的最低可用客户端版本；兼容判定仍以实际能力为准。新包宣称也支持早期客户端时，必须用该客户端实际导入并消费，不能只改索引标签。

例如，给已启用上下文增加一张沿用原楼层与坐标接口的地图时，导出同一 `packageId` 的新 `resourceVersion`，更新地图索引、该图资源及 `files`。当该上下文的 provider 和能力无变化时，包格式、组件语义版本及客户端构建均可沿用。若地图需要客户端目前无法读取的楼层接口，先部署支持该接口且仍能消费历史包的客户端，再发行声明新接口能力的包。

### 激活、读取与失败恢复

1. 下载或本地导入走现有资源入口。先按所选 reader 解析清单和必需能力，再检查文件库存、路径、大小、摘要和绑定；制作预检与运行时消费使用同一语义。区分可读、已安装、可启用和已启用状态，给出对应缺失能力或依赖。
2. 在暂存区准备候选版本，验证该次切换涉及的上下文及依赖。复用资源写锁、会话空闲租约与 catalog 恢复事务；对局内维持已启用快照。新版本激活和受影响显示依赖的选择一次提交。取消、校验失败或空间不足时，原已验证版本继续可用；提交阶段中断按既有恢复流程收敛到一个完整可用版本，再开放消费。连续重试同一候选不产生第二份选择。
3. 资源服务发布新快照后，由 UI 线程更新受影响的上下文和稳定卡片。provider、结构/控件缓存及默认或作者显示缓存按实际资源身份失效。worker 捕获相关请求、会话、帧、地图、楼层及资源快照；切换、回退、关图或结束本局后旧工作取消，迟到结果不能提交身份、位姿、图片或提示。导入进度和恢复不依赖页面是否可见。
4. 资源回退通过验证后重新激活上一可用版本。重新检查依赖和每层显示绑定，按同一路径失效旧任务与缓存。历史资源、作者路线和用户图库继续保存在原处；即使某条路线暂不可用，也保留记录及原因，以便回退后恢复选择。发行客户端降级另做测试，确保老客户端能通过其原路径重新使用旧包；若 catalog 演进影响读取，须保留可恢复的旧选择与旧版本，给出经测试的恢复入口。

### 兼容与降级情形

| 情形 | 预期行为 |
| --- | --- |
| 已支持的旧包新导入，或安装库随客户端升级保留 | 按原格式解析，使用对应旧语义及实际资源。保留组件身份、设置选择和用户数据。S0 格式 1 的银行字段缺失按原格式处理，格式 2 仍核对 `bankId`、`generatorVersion` 及内容。 |
| 已发布旧格式缺当前 provider，包括旧整合入口在内的待核历史制品 | 第 1 版核对制品与发布记录。原有可用路径缺失时，按第 4 项决策补读取路径，证明旧包无修改即可恢复原有功能；发布制品缺失或旧语义还原不了时记录具体欠项，暂不宣称已经达到兼容目标。 |
| 新客户端导入新包，但缺少协议、必需能力或不可替代的资产 | 解释具体缺口；保持上一可用版本。没有历史版本的上下文保持不可用。格式损坏和缺能力分开反馈，无需删旧包才能处理。 |
| 较早客户端仍在使用，或从新客户端回退 | 按较早客户端实际能力提供历史包或已验证等价的旧格式发行物。未知格式交由旧 reader 原有行为处理；用实测确认新版资源试装失败和程序降级后仍能继续选用旧包。 |
| 新结构包无作者路线，或作者绑定不匹配 | 在当前层提供合格的默认底图，兼容作者继续可用，冲突作者暂不可用并说明原因。作者文件和用户路线保持可恢复，身份与结构贴合走同一基础链路。 |
| 旧包缺可选导航字段 | 本地基础能力按其原契约使用。涉及路线广场时，沿用 #163 已登记历史网格的校验，旧缺字段与显式不支持的导航声明分别处理。未知模板或网格缺口保留原图库，提示相关功能的可用范围。 |

## 识别与验证方案

未来实现只通过 provider 给现有识别和贴合链路供数，困难与噩梦共用识别、楼层、贴合与生命周期逻辑，资源 profile 表达已有的参数、楼层和坐标差异。制作端准备 fast 数据和已支持的控件资源；运行端按真实 provider 读取，验证身份、楼层及坐标，再沿现有证据、当前帧校验与提交规则产生结果。包内提示、控制资产或显示图不能自行授予身份、楼层或位姿。新包需要改候选、阈值、楼层规则、相似组成员或最终接受条件时，把实际样本和行为差异交人工确认，由后续独立识别工作处理。

各阶段用冻结客户端构建、实际包版本/既有摘要和具体资源选择记录证据。在真实入口做以下对照。

- **旧包回归**覆盖两赛季、两模式及发布过的格式分支，在干净安装和带旧库存升级后分别检查导入、重启、可用上下文、地图/楼层、贴合、基础与原有作者显示、切回旧版和图库保留。测试用原包进入现有导入/provider/Qt Session，历史真值只在结果出来后比对。
- **新图端到端**用同一个 Windows 构建先确认旧包中没有目标新图，再只导入新结构包，按范围记录新图首次正确可见像素、换层、关图重开、手选入口、无作者底图与资源回退。在资源库隔离的干净安装上核对实际消费文件来自试验包及声明依赖。困难与噩梦分别记录其实际输入与调用参数；用真实资源回放做可重复回归，另行完成 Windows 游戏实测。
- **失败与交错操作**覆盖缺必需能力、文件损坏、错误层/坐标绑定、同版本异内容、取消和提交中断、换资源后的迟到结果、关闭游戏地图或结束对局。验证旧版本或恢复入口可继续使用，并检查实际 provider 与可见像素。
- **性能**沿用首贴约 500 ms、锁图且首贴成功后重新开图约 300 ms 的目标。分别记录计算耗时和从输入到首次正确可见像素的时延，给出样本数、p50/p95/max、未显示次数及有图像真值支持的错层次数；回放和实机证据分别记录。发布与实机验收沿用项目现有流程。

## 待人工决策点

下列选项均未选定。每项给出最晚需要定案的阶段及其影响。

| 编号 | 决策 | 选项与利弊 |
| --- | --- | --- |
| 1 | 首批新图覆盖范围，第 1 版明确样本 | **A. 已支持赛季/模式内的新图**，边界清楚、验证成本较低，但未来赛季需要后续支持。**B. 同时纳入复用现有机制的新赛季**，用户可仅用结构包进入更多地图，但依赖第 2 项放开上下文发现，并增加采集、楼层、设置和实际样本验证。新机制走客户端功能排期。 |
| 2 | 赛季/模式准入的权威来源，第 2 版前定案 | **A. 客户端登记具体上下文，包提供地图**，准入简单、易复核，每个新赛季需更新客户端。**B. 客户端登记 provider/profile，结构包在其范围内声明上下文**，兼容新赛季可随包接入，但须校验实际机制、处理身份冲突及激活顺序。**C. 官方资源目录授予上下文，包引用其登记**，便于集中复核与撤回，但引入目录版本、离线使用与目录/包一致性问题。 |
