# 结构包独立更新规划

本规划仍为草稿。十项产品与架构决策已由人工定稿，版本阶段、字段名称和示例用于指导后续实施。任务来源见 [Issue #186 第 1 条](https://github.com/chenhuanh9-a11y/xiaochao-assistant/issues/186)。

## 目标与边界

约 3–4 个客户端版本内，让已具备相应能力的正式 Windows 客户端通过导入并启用新版结构包，就能识别新地图、判断楼层、完成首贴和关图重开后的贴合，并显示与当前结构逐层对齐的默认底图。首批只在已支持的赛季和模式内新增地图。验收时固定同一客户端构建，更新前后只改变结构包，无作者路线时也要完成基础流程。有兼容路线时核对其实际显示。首发验收覆盖识别、贴合、路线显示和旧包兼容，图库编辑、路线广场及安卓互通延后。

历版已支持的旧结构包继续支持原包导入、已安装版本重启后使用、切换及回退。兼容清单以历版发布、明确交付的制品及其原有功能为准。用户无需重新下载、改包或先删旧包。每个阶段都验证旧包的实际消费者；格式缺失字段与显式不合法值分别处理，继续执行各历史格式原有的完整性、所有权和坐标校验。

沿用 [#171 的 1.1.9 事实报告](structure-pack-only-facts.md)及 [#175 的源码链接修正](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/175)。设计接缝对应报告中的[资源链路](structure-pack-only-facts.md#资源链路入口到最终消费者)和[能力缺口](structure-pack-only-facts.md#逐项能力与缺口)。其中的版本与 PR 状态保留历史基线。本规划采用 #186 的最新项目边界；路线广场导航的缺字段兼容以已合入的 [#163](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/163) 为准，四范围互通 [#134](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/134) 仍是独立草稿。

| 变动 | 客户端与结构包的责任 |
| --- | --- |
| 已支持上下文的新地图或几何修订 | 包交付稳定地图/楼层标识、结构及其 fast 派生、坐标与绑定、适用控件及底图所需数据。客户端负责实际识别、楼层判断、贴合与渲染，仅在这些数据能由已发布能力完整消费时成立。 |
| 新赛季沿用已支持的机制 | 留待后续扩围评估。先确认赛季/模式身份、采集条件、provider、楼层语义和实际资源均匹配客户端声明的能力。 |
| 新游戏机制或新运行时能力 | 新采集协议、识别/接受规则、楼层状态机、控件类型、坐标语义及客户端尚无实现的模式，需要先由客户端支持。客户端实现、测试并声明新能力后，资源才可选择依赖它。 |
| 作者图、自定义路线与广场 | 作者路线独立分发，继续按 #168 的逐层结构与坐标绑定选用。图库、广场及安卓网格的可用性按各自能力验证。它们的资产与数据不得改变识别身份、楼层和结构位姿。 |

## 未来 3–4 个客户端版本

以规划获批后启动的下一版计为第 1 版，以下是实施顺序与退出条件，具体版本号由发版列车确定。每阶段保留已支持旧包的回归证据，失败时保留原可用资源和上一阶段承诺。

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| 第 1 版 · 确立旧包兼容 | 以实际发布清单和留存制品核对历史格式、导入状态与 provider。保留按格式分派的旧读取路径，缺失路径在实现工作中补齐。验证原样导入、已安装库直读、Setup 升级保留、重启和资源回退。导出与导入对现有契约做正反例往返。 | 困难和噩梦均覆盖发布过的格式和上下文，已有识别、楼层、贴合、底图及可用作者路线行为无回归。缺历史包或缺消费路径单列为未验证或待补齐，历史发布包须用原制品验证。 |
| 第 2 版 · 打通新契约 | 在现有结构清单内实现版本化描述。把结构包的能力引用接到导出、导入、启用、provider、页面及会话上下文，和旧读取路径并行。用两模式资源验证共用链路，演练能力不匹配、缺依赖、上下文冲突和中断恢复。 | 已部署试验客户端能分别装载旧包和试验包。旧客户端尝试导入不受支持的新契约时保留原选择与可用资源。能力不匹配的包无法启用。 |
| 第 3 版 · 用固定客户端验收 | 用同一构建先运行旧包，再导入一份含真实新图的完整结构包。验证手动导入和官方索引、确认更新后空闲启用、逐层默认底图、路线显示、换层、重开及回退后旧图可用。相似组沿用现有复核名单。 | 干净 Setup 和带历史资源的升级路径均跑通。真实游戏记录覆盖两模式的受影响入口、新图可见结果和旧图回归。通过后按首发基础玩法范围交付。 |
| 第 4 版 · 补齐差额 | 第 3 版有缺口时，集中处理对应的兼容、资源链路或消费路径，重新做固定客户端验收。已达标后的扩围单独排期。 | 同一前后对照仍可成立。超出客户端能力的地图随相关客户端功能排期，资源发布说明按已验收范围承诺。 |

## 结构包契约与清单演进

### 版本和字段

现有 `formatVersion` 已区分通用格式 1 与控件银行格式 2，现有 reader 对包、组件和上下文对象执行严格字段校验。新能力在现有结构组件清单或入口描述上做版本化扩展，沿用外层包格式和严格字段校验。下表的字段名用于设计示例，具体落点在实施时对照两模式的消费者确定。基线字段与校验见[事实报告中的格式与客户端能力版本](structure-pack-only-facts.md#逐项能力与缺口)及 [1.1.9 清单源码](https://github.com/chenhuanh9-a11y/xiaochao-assistant/blob/502ec2a9c690a6d0d3e7b25f5cba8b78f51585b5/app/imported_resource_packages.py#L27-L48)。

| 层级 | 继续使用的字段或拟扩展的声明 | 解析和验证 |
| --- | --- | --- |
| 包容器与资源身份 | `schema`、`formatVersion` 区分解析方式。`packageId`、`resourceVersion` 延续包身份与数据版本；版本目录保持不可变，已有 manifest 摘要用于识别实际版本。 | 相同版本及内容可重复导入。相同身份而内容不同视为冲突。发新地图不要求更改客户端版本或数据格式。 |
| 客户端能力 | 复用 `clientCompatibility.resourceProtocol`、`requiredCapabilities`。每个候选声明全部必需的协议与版本化能力。官方索引可镜像这些信息用于筛选，包及实际 provider 校验负责最终判定。 | 客户端公布已实现的能力。必需能力未知、版本不匹配、协议不支持或声明低于实际使用的能力时，在启用前报告具体缺口。 |
| 组件和上下文 | 沿用 `components[].type`、`schemaVersion`、`contexts`、`entrypoint`、`dependencies`、`files`。在版本化结构描述中，用 `season`、`mode` 关联客户端已支持的运行能力，例如 `runtimeProfile` 标识。赛季、模式显示名归显示元数据。 | 同一解析结果服务导出预检、导入、启用、provider 和 UI。声明须匹配组件所属上下文与实际运行能力，首批还须属于已支持的赛季和模式。重复或冲突的上下文拒绝启用。结构包只可引用已有能力，声明不能加载代码或指定任意 provider 路径。 |
| 地图和楼层 | 复用基础组件入口的 `runtimeInterfaces` 和其现有索引。已有接口表达不足时，才在有版本的组件语义中补 `mapId`、`floorId`、结构引用与版本键、坐标空间和参考画布、控件绑定及默认底图绑定。 | 身份、结构和楼层索引只保留一处权威定义。地图 ID 在同一赛季和模式内稳定，楼层 ID 在同一地图内稳定，更新时保留已有语义。引用须能在库存和依赖内解析到实际文件、相同上下文和楼层；缺失必需几何、派生数据或坐标绑定不得授予可用性。 |
| 可选能力 | 候选用明确的可选扩展区容纳可跳过的显示元数据。作者路线、导航与图库的绑定沿用相应组件或协议，分别检查实际资产。 | 只忽略在已知格式内明确声明为非必需、且任何必需组件都未引用的数据。未知事实不得默认成通用控件、任意坐标变换或空相似组。 |

解耦以后，`resourceVersion` 跟地图资产发布走，`formatVersion` 跟包解析结构走，组件 `schemaVersion` 跟组件语义走，客户端通过已实现的协议、profile 与能力决定是否可用。需要向用户提示升级时，可显示发布方已验证的最低可用客户端版本；兼容判定仍以实际能力为准。新包宣称也支持早期客户端时，必须用该客户端实际导入并消费，不能只改索引标签。

例如，给已启用上下文增加一张沿用原楼层与坐标接口的地图时，导出同一 `packageId` 的新 `resourceVersion`，更新地图索引、该图资源及 `files`。当该上下文的 provider 和能力无变化时，包格式、组件语义版本及客户端构建均可沿用。若地图需要客户端目前无法读取的楼层接口，先部署支持该接口且仍能消费历史包的客户端，再发行声明新接口能力的包。

### 激活、读取与失败恢复

1. 每次发行完整结构版本，沿用显式组件依赖。手动导入和官方索引下载使用同一完整包。下载时继续按官方索引核对包的字节数与 SHA-256，两条入口均走清单和文件校验。按格式分派 reader，使用该格式的解析、完整性、所有权与坐标规则，再核对实际库存、绑定及必需能力。区分可读、已安装、可启用和已启用状态，说明缺失的能力或依赖。
2. 准备完整候选版本，预检涉及的上下文与依赖，向用户说明更新影响。用户确认后，更新等待客户端空闲并取得既有资源租约。等待期间当前资源继续可用，对局使用原快照。取得租约后在资源写锁内复核已确认的候选与依赖，经 catalog 事务一次切换结构版本和受影响的显示选择。提交前可取消，校验失败或空间不足时继续使用原版本。提交阶段中断沿用既有恢复流程，恢复至完整版本后开放消费。重试同一候选沿用同一版本选择。
3. 资源服务发布新快照后，由 UI 线程更新受影响的上下文和稳定卡片。provider、结构/控件缓存及默认或作者显示缓存按实际资源身份失效。worker 捕获相关请求、会话、帧、地图、楼层及资源快照；切换、回退、关图或结束本局后旧工作取消，迟到结果不能提交身份、位姿、图片或提示。导入进度和恢复不依赖页面是否可见。
4. 资源回退通过验证后重新激活上一可用版本。重新检查依赖和每层显示绑定，按同一路径失效旧任务与缓存。历史资源、作者路线和用户图库继续保存在原处；即使某条路线暂不可用，也保留记录及原因，以便回退后恢复选择。发行客户端降级另做测试，确保老客户端能通过其原路径重新使用旧包；若 catalog 演进影响读取，须保留可恢复的旧选择与旧版本，给出经测试的恢复入口。

### 兼容与降级情形

| 情形 | 预期行为 |
| --- | --- |
| 已支持的旧包新导入，或安装库随客户端升级保留 | 按原格式解析，使用对应旧语义及实际资源。保留组件身份、设置选择和用户数据。S0 格式 1 的银行字段缺失按原格式处理，格式 2 仍核对 `bankId`、`generatorVersion` 及内容。 |
| 已发布旧格式缺当前 provider，包括旧整合入口在内的待核历史制品 | 第 1 版核对制品与发布记录。对于确认受支持且缺失读取路径的旧格式，补齐对应 reader/provider 后用原包验证原有功能。保留按格式分派的旧语义，分派发生在资源读取时。缺制品或旧语义无法还原时，记录具体缺口及未验证的功能。 |
| 新客户端导入新包，但缺少协议、必需能力或不可替代的资产 | 解释具体缺口；保持上一可用版本。没有历史版本的上下文保持不可用。格式损坏和缺能力分开反馈，无需删旧包才能处理。 |
| 较早客户端仍在使用，或从新客户端回退 | 按较早客户端实际能力提供历史包或已验证等价的旧格式发行物。未知格式交由旧 reader 原有行为处理；用实测确认新版资源试装失败和程序降级后仍能继续选用旧包。 |
| 新结构包无作者路线，或作者绑定不匹配 | 使用结构包附带的当前层默认底图，兼容作者继续可用，冲突作者暂不可用并说明原因。作者文件和用户路线保持可恢复，身份与结构贴合走同一基础链路。 |
| 旧包缺可选导航字段 | 本地基础能力按其原契约使用。涉及路线广场时，沿用 #163 已登记历史网格的校验，旧缺字段与显式不支持的导航声明分别处理。未知模板或网格缺口保留原图库，提示相关功能的可用范围。 |

## 识别与验证方案

未来实现通过 provider 给现有识别和贴合链路供数，困难与噩梦共用识别、楼层、贴合与生命周期逻辑，资源 profile 表达已有的参数、楼层和坐标差异。制作端准备 fast 数据和已支持的控件资源。运行端按实际 provider 验证身份、楼层及坐标，沿现有证据、当前帧校验与提交规则产生结果。默认显示资产逐层核对地图、楼层、结构版本键、坐标空间、参考画布及配准变换，渲染沿用该层绑定，识别仍以结构为准。相似组严格沿用项目现有复核名单，未登记的新图保持独立。依赖新增登记或变更候选、阈值、楼层规则及最终接受条件的地图延后，需要提供实际样本和行为差异，由独立识别工作处理。

各阶段用冻结客户端构建、实际包版本/既有摘要和具体资源选择记录证据。在真实入口做以下对照。

- **旧包回归**覆盖两赛季、两模式及发布过的格式分支，在干净安装和带旧库存升级后分别检查导入、重启、可用上下文、地图/楼层、贴合、基础与原有作者显示、切回旧版和图库保留。测试用原包进入现有导入/provider/Qt Session，历史真值只在结果出来后比对。
- **新图端到端**用同一个 Windows 构建先确认旧包中没有目标新图，再只导入新结构包，记录首次正确可见像素、换层、关图重开、逐层默认底图、兼容路线显示与回退。在资源库隔离的干净安装上核对实际消费文件来自试验包及声明依赖。困难与噩梦分别记录实际输入与调用参数，用真实资源回放做可重复回归，另行完成 Windows 游戏实测。
- **失败与交错操作**覆盖能力不匹配、索引字节数或 SHA-256 校验失败、文件损坏、错误层或坐标绑定、同版本异内容、对局中等待空闲、取消及提交中断、切换资源后的迟到结果、关闭游戏地图或结束对局。验证旧版本或恢复入口可继续使用，并检查实际 provider 与可见像素。
- **性能**沿用首贴约 500 ms、锁图且首贴成功后重新开图约 300 ms 的目标。分别记录计算耗时和从输入到首次正确可见像素的时延，给出样本数、p50/p95/max、未显示次数及有图像真值支持的错层次数；回放和实机证据分别记录。发布与实机验收沿用项目现有流程。

## 已定稿的决策

| 编号 | 决策 | 结论 |
| --- | --- | --- |
| 1 | 首批覆盖 | 在客户端已支持的赛季和模式内新增地图。 |
| 2 | 赛季与模式准入 | 结构包声明并引用客户端已支持的运行能力。准入要求能力声明、赛季与模式、实际 provider 及资源匹配。 |
| 3 | 清单扩展 | 在现有结构清单体系内做版本化扩展，沿用外层包格式。 |
| 4 | 旧格式读取 | 保留按格式分派的旧 reader/provider。以受支持旧包原样使用且既有功能无回归作为验收条件。 |
| 5 | 发布粒度 | 只发布完整结构包。 |
| 6 | 启用时机 | 用户确认更新后，在客户端空闲时取得资源租约并切换启用。 |
| 7 | 默认底图 | 结构包附带逐层配准的默认显示资产。 |
| 8 | 相似组登记 | 首批严格沿用项目现有复核名单，包内新登记延后。 |
| 9 | 分发与校验 | 沿用手动导入和官方索引，维持现有字节数与 SHA-256 校验。发行物加签留作后续增强。 |
| 10 | 首发验收 | 覆盖识别、贴合、路线显示与旧包兼容。图库编辑、路线广场及安卓互通延后。 |
