# 地图资源导入与加载：前后实测

本批四模式、八个真实包中，首次导入并启用的中位数由手动路径 167.6 秒降至 138.9 秒（减少 17.1%），下载后导入路径由 170.5 秒降至 138.0 秒（减少 19.0%）。新进程加载的部分模式改善很小，S1 困难首次读取反而更慢，不能概括为所有加载都变快。

## 来源与方法

- 基线：`502ec2a9c690a6d0d3e7b25f5cba8b78f51585b5`；候选产品及同一测量工具：`53333627af648296962f0764aa8b7efdcccdc09f`。报告提交只增加/修正文档与证据，产品与工具文件须与候选相同。
- 同一 Windows 11 22631、Intel64 Family 6 Model 198 Stepping 2、20 逻辑核、33780793344 字节可见内存；Python 3.13.3、NumPy 2.2.5、PySide6 6.11.1、OpenCV headless 5.0.0.93、Pillow 11.2.1。依赖和机器字段逐样本一致。原包及隔离库存均在 E: NTFS 固定盘，总容量 2048390066176 字节；空闲容量和 CPU/进程快照逐份保留。磁盘物理型号未能读取，不称为冷盘测量。
- 24 份正式结果：两版 × 手动/下载后导入 × 导入/加载 × 3 次，全部完成，无服务错误。每次导入为新隔离库存，八包按 S0 噩梦、S0 困难、S1 噩梦、S1 困难的“结构→路线”顺序进入真实 `ImportedResourceService`。下载路径从已下载的原包调用 `importVerifiedArchive`，含实际身份/大小/摘要绑定，**不含网络下载时间**。
- 导入起点是服务方法调用前，终点是相应 `importCompleted`、`inventoryLoaded=true`、`busy=false`、无待确认计划及最终库存核对。保存、启用、可用模式刷新均在终点前，没有把重复工作移到终点后。
- 每个加载样本另起 Python 进程，先 `listPackages`，再依次对四模式做首次 `prepare_context` 和真实基础/控件、作者像素消费核验，随后同进程再读四模式。整批加载总时长包含列表和两遍；下文逐模式时长才分别对应首次、重复读取。阶段和不当作独立端到端计时。
- “新进程首次”只说明该进程内该模式第一次准备，不包括进程启动/Python 模块导入，不代表物理磁盘缓存被清空。未清理用户或系统缓存，计时前的输入摘要读取也可能预热文件缓存；未停止或隔绝其他机器负载。第一轮基线取自前一日的完整有效结果，其余样本在次日接续交替运行，UTC 起止与环境快照都保留，不能用这些数字外推所有电脑或每次体验。
- 实际入口为 `python tools/benchmark_imported_resource_service.py --repo <对应源码目录> --source <原包目录> --store <隔离库存> --output <结果JSON> --scenario import|load --transport manual|verified`；每份记录绑定实际源码提交、14 个实际模块来源、八包身份和计时端点。资源路径、消费者、错误和阶段均走生产函数，计时包装不替换其实现。

## 保留的慢阶段及必要理由

保存仍需完成归档/路径/尺寸/CRC 与载荷摘要、暂存拥有树及实际发布后库存证明，挡住坏包；最终同句柄归档哈希不能删，Windows 真实元数据恢复反例已证明其必要。保存时间也含写盘与同步，不能全称为检查成本。

启用事务仍读取基础/控件和作者实际数据，验证错模式、错组件与依赖不匹配，保留原 S0 模板及作者逐层结构/坐标标准。最终退出读域的载荷复验同样保留：首稿删除它后，远端既有测试真实复现“库存校验后图片被改写却仍提交”，现已恢复为基线实现；跨包与作者身份核对期间的实际改写也有回归。普通列表只扫清单；活动模式投影仍逐文件核对基础/控件，避免把本次已变动文件当成可用。新进程构造实际消费者需要这些解码结果，不借优化改变准入或识别规则。

同进程重复读取的改善不一致：手动库存 S0 噩梦中位数 796.4→799.6 毫秒，基本持平且略慢。S1 困难首次读取在手动库存为 6000.4→6137.1 毫秒，下载库存为 5870.5→6187.2 毫秒，均未改善。没有为提高指标删除失败样本、放宽语义断言或改变模式规则。
