# 其他电脑没有体现资源导入提速：性能路径调查

## 给 huan 的结论

1.1.8 的提速代码已进入当前 `main`，也进入了记录为 1.1.8 性能候选的 Windows Setup 源码版本；资源页运行时会调用这条代码路径。可确认的是「源码有改动、构建配方会收集对应程序模块、开发机曾有一次真实资源服务计时」，不能据此确认另一台电脑安装的二进制确实含有同一代码，更不能说其他电脑性能已通过。

当前最有力的解释是测量覆盖不足加上本机热态差异：提交到进程内的语义复用在程序新开时为空，新导入的版本也会产生新的资源身份；它不跨电脑共享。旧计时每个场景只有 1 次，且没有清空操作系统缓存。资源包读取、解压、文件核验和库存扫描仍是实际路径的一部分，冷机器的磁盘、杀毒扫描、资源数量和输入包差异都可能主导总耗时。**没有故障电脑上的程序文件校验、资源包摘要和分段计时，因此不能确定是哪一项造成了感受差异。**

建议先在隔离的 Windows 资源目录复测并记录阶段耗时、输入包摘要和安装来源；不要清理真实用户缓存。若某台电脑仍没有相同版本的导入代码，再按其 Setup 类型和程序文件校验值核实升级是否真正替换文件。

## 范围与相邻模块

- 主模块：**地图资源**；安装包是否携带同一代码及更新替换情况归 **安装与更新**。
- 只追踪 **地图识别** 对已启用基础资源的调用，以及 **自定义图库**、**路线显示** 对已启用作者路线的消费。本报告没有修改这些模块；路线显示仅消费已授权资源。
- **排查与帮助** 的错误来源修复与开放 PR #164 有读范围交叠。本分支不修改诊断，也不把 #164 当作性能修复。
- 本分支仅新增调查报告；没有修改产品代码、测试、素材、生产资源或打包配置。

## 已证实的性能路径

### 代码已进 main

从当前 `main` 祖先历史和工作树核对：

- `207b3a1` 在一次资源准入操作内共享实际读取证明，避免语义核验中重复打开并重读同一组件声明；作用域结束仍核对实际消费的文件和当前资源状态。
- `2adeb74` 加入当前 `ImportedResourceService` 生命周期内的语义资格复用，限制为最多 32 项；同一基础上下文的多个冷资格校验最多并行 2 个。复用仅覆盖纯语义结果，不保留引擎、文件健康或启用授权；复用时仍重新证明输入文件。
- 同一提交合并了导入后的库存刷新：保存后先读库存但延后可用模式核对，成功启用后由最终刷新完成库存和可用状态，失败、取消或中止计划时也会补做最终刷新。
- `d8f1958` 是 1.1.8 性能候选版本提交，父提交是 `2adeb74`。PR #161 的合入说明记载了干净生产构建与冻结程序自检通过。其后 `06ee7fb` 只调整发布边界测试。当前 `main` 位于 1.1.8 紧急修复之后，包含这段历史。

这些结论证明代码在当前源码树。`client.py` 创建 `ImportedResourceService`，启动后先列资源；资源页导入和启用通过该服务进入被优化的激活逻辑。`qt-client.spec` 收集 Qt 客户端源码模块，PyInstaller 从 `client` 入口分析程序模块，冻结检查还核对客户端和共享程序文件。因此构建规则包含这条链路。

这仍不证明任意另一台电脑上的运行时一定走到该代码。服务器没有可检查的 Windows Setup 或其他电脑的安装目录；不能从本轮静态检查验证那个 `.exe` 的文件闭包、安装升级替换结果、杀毒隔离情况或实际运行分支。PR #161 留存的 Setup 来自包含优化提交的候选源码，但本轮没有读取 Setup 本体再次核对哈希。

### 复用对冷设备的边界

`SemanticQualifications` 属于单个 `ImportedResourceService`，随当前客户端进程创建；缓存键绑定资源根目录身份、赛季/模式、选中组件版本与摘要，以及解析器能力和登记引用。命中时仍执行真实资源读取/当前性检查。由此可知：

- 进程重启会从空缓存重新开始；不同电脑不会共享该缓存。
- 新导入的资源版本有不同版本/清单身份，不会继承旧版本的语义资格。
- 多个独立冷上下文可以同时启动两个核验任务；单一上下文仍串行，且存档解包和文件发布不因此并行。
- 同一进程重复启用相同资源可能跳过引擎构建和作者显示语义解码，但必须重新证明输入。它不能证明首次导入或另一台冷机器会有相同加速。

库存也不是缓存结果：不带完整核验的列表读取仍会遍历本机所有包版本、读取并解析清单、检查入口文件；用户要求完整刷新时还会校验版本库存。导入包的完整保存包含 ZIP 校验、解压和逐文件摘要检查。在线验证导入会先完整检查 ZIP，再保存并再次解压；发布前还会重开源文件核对摘要和稳定性。安全校验不应被关闭，这些读取会让包大小、文件数量、存储介质和系统文件缓存直接影响结果。

在当前源码中没有发现依赖开发者个人目录、开发环境变量，或在包缺失时转向开发者本地资源的路径。此结论只排除了这几处静态回退；它不能替代在故障电脑确认真实程序文件与资源目录。

## 对 PR #161 计时的复核

PR #161 合入说明记录了四种赛季/模式下真实资源服务的导入与自动启用，并报告：结构包约 17–22 秒、路线包约 24–27 秒、暖态首次路线删除约 17–20 秒，冷态首次删除约 43.5 秒。它同时明确每个场景 `n=1`、没有清理操作系统文件缓存。其证据边界如下：

| 核对项 | 可从记录确认的内容 | 仍缺的内容 |
| --- | --- | --- |
| 输入 | 使用真实资源包，经资源服务导入/启用；覆盖四种上下文 | 包文件名称、大小、SHA256、每个包包含的文件数没有列在合入摘要中 |
| 计时端点 | 资源服务操作，覆盖导入/自动启用或删除 | 未记录从选择文件到首次正确可见像素的 GUI 端到端时间；没有真实游戏结果 |
| 环境 | Windows 产品构建/冻结自检在合入摘要中记录通过 | 具体电脑 CPU、磁盘、Windows 版本、杀毒状态和分阶段耗时未列；操作系统缓存没有清理 |
| 样本 | 每场景一次 | 无法计算 p50/p95/max，也不能估算跨机差异或稳定性 |

因此这些数值能说明开发环境有一次服务级操作结果，不能证明其他电脑变快、不能证明冷读性能，也不能将删除数字外推为导入耗时。冷态 43.5 秒仍高于当时约 20–30 秒目标；应保留为待复测，不应称达标。

## 可能仍占主导的阶段

这几项是从当前实现推导的测量重点，不是本轮发现的性能缺陷：

1. **选择与检查 ZIP**：在线下载验证会先扫描压缩包成员、解压并检查每个载荷；保存时再次解压到隔离目录并校验每个文件摘要。保存前后的文件身份与内容摘要核对还会读取源包。手动导入不额外走下载前检查，但仍需保存阶段完整核验和发布前来源复核。
2. **语义核验与建引擎**：新版本的第一次激活仍须为选中上下文建临时引擎并解码作者显示。四个独立冷上下文最多两路并发；该步骤不是跨设备预热。
3. **库存与可用状态刷新**：代码把可用上下文扫描合到最终刷新，但仍需扫描保存的版本和核对当前目录/清单。资源数量、文件大小、磁盘缓存和杀毒实时检查都可能影响耗时。
4. **失败重试**：失败重试不是提速路径。保存成功后自动启用失败会保留完整包并报告未启用；不能把这类失败与“加载慢”混为一谈，也不能以关闭校验换取表面速度。

## 待实包确认与 Windows 核验清单

需要在目标电脑的隔离副本上逐项记录：

1. 星图显示版本、Setup 类型与来源；核对程序内主要 Qt 客户端文件的版本/摘要，确认安装器实际替换到包含优化的文件。若走 QtIFW 同版本更新路径，还需核对内部组件更新是否执行。
2. 输入 ZIP 的来源、字节数、SHA256、清单包版本、组件/载荷数量；核对资源库存已有版本数。记录安装目录所在磁盘、可用空间，以及 Windows 安全软件扫描状态。
3. 在临时隔离资源根运行真实资源服务，分开记录 ZIP 检查、保存解压、逐文件摘要、语义建引擎、资源库存、自动启用和最终可用状态的耗时。采集至少 20 个有代表性的操作后报告 p50/p95/max、失败数和取消数；另把首次冷启和同进程重复启用分开统计。
4. 不清理真实用户缓存、不覆盖当前安装、不删除任何用户资源。需要研究冷盘读取时，用隔离的测试数据和新临时目录；说明无法清空系统缓存，因此仍不是严格 OS 冷缓存实验。
5. 如果关心用户实际体验，再单独计时从选择文件到资源页显示正确启用结果；若要测游戏中首个正确像素，必须有明确输入图像真值，并与资源服务耗时分开报告。
