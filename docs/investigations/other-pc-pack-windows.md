# 其他电脑导入与加载：Windows 实际产物调查

## 给 huan 的结论

已经证实两件容易混淆的事：**同样显示 1.1.8 的程序，实际可以是不同代码；同样叫 S0/S1 结构包或作者路线包，实际也可以互不配套。** 本轮找到了初版和紧急修复版的实际安装包，重新计算文件校验值、用 Qt 官方工具解包，并核对程序代码和依赖。未发现这两份交付包缺少所查导入模块或运行依赖的证据。

初版 12 个路线包都依赖初版结构，紧急修复版 14 个路线包都依赖新版结构；交叉搭配时全部不满足精确依赖。这里说明的是确定的兼容边界，**尚未证明反馈中的电脑混用了包**。同版更新没有替换到修复程序、旧资源目录尚未迁入、本机数值重算差异，则是已有源码和修复记录支持的其他排查分支，不能把其中任何一个直接当成该电脑的结案根因。

影响范围是「地图资源」的保存、启用、库存与重新加载，以及「安装与更新」中程序身份和同版替换的区分；「排查与帮助」仍可能丢失旧错误的来源。未取得故障电脑的实际程序身份、安装替换结果、原始操作顺序与脱敏错误，因此**没有闭环个案根因，没有修复产品，也没有完成用户电脑或游戏验收**。建议先按实际程序和包摘要配对，再沿保存、启用、重新加载分段核对；不要先改识别逻辑或清理真实缓存。

## 本轮实际运行与边界

运行前核对了现有静默入口：`--self-check` 在创建窗口、单实例锁、采集和快捷键之前返回；生产数据固定在实际 EXE 旁，不能靠 `--sandbox` 改向。因而仅在官方工具提取出的本任务副本中运行，未绕过锁或修改权限。子进程工作目录在源码树外，去除 Python/产品资源环境变量，PATH 仅保留 Windows 系统目录，个人数据和临时目录也指向本任务目录。

两版实际冻结程序分别运行 `星图.exe --self-check`，退出码均为 0；初版 753ms、修复版 1046ms，各 n=1。`frozen/ready/qml=true`，`nativeInputStarted/windowsCreated/listenersStarted/captureStarted=false`。这是依赖与启动前检查，**不是导入耗时、GUI 或游戏验收**。

冻结程序没有现成的无界面资源导入 Service 命令，旧导入助手处理的是历史作者格式，不能替代当前生产链。本轮没有向冻结程序注入脚本或新开关：真实导入和自动启用由基线源码的 `ImportedResourceService.importArchive` 执行；冻结程序只验证重新加载结果。两者分开记录，不称为“冻结 Service 导入通过”。

源码探针创建独立的 RuntimePaths/ResourceResolver/资源工厂/LiveRuntime/SessionService，再给真实服务配置资源租约。没有启动客户端主界面或游戏调用；输入是实际交付包，保存、准入、语义校验、自动启用、库存发布均执行原实现，没有替换求解或注入正确答案。原始事件记录保存、配套核对、激活到最终空闲的阶段时间。
