# 其他电脑结构包和资源包导入失败：根因与影响调查

## 给 huan 的结论

1.1.8 确实有一处会因电脑数值计算差异而拒绝有效资源包的缺陷。#162 已把这类数值等价检查移到制包端，并保留客户端的数据格式、完整性、绑定和上下文检查。另一个可能让电脑继续运行旧代码的因素是 QtIFW 对同版本更新不替换文件，#162 也提高了内部组件版本来触发替换。

目前只能确认代码中存在过这两类问题，不能确认反馈中的那台电脑究竟命中了哪一类：没有该电脑的 1.1.8 安装包类型、程序文件校验值、导入阶段和脱敏错误信息。#164 只补错误诊断，不是修复，也不能作为已复现或已解决的依据。未发现证据表明失败会发布半份资源目录或半个启用目录；但导入保存成功、启用失败时，完整包版本可能留在资源库存里，界面应显示“已保存但未启用”。

## 证据与判定

### 已证实：客户端本机重算造成机器相关误拒收

PR [#162](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/162) 的提交 `f727f9f72fe8da2821fd95d2dadee2b625f79e1b` 改了两项客户端准入：

- **S0 楼层控件**：此前启用时会在当前电脑重新载入一份数值模板，并将导入包中的模板数组与本机模板逐值比较。现在仍检查声明的类型、形状、有限值、归一化、模板族、模式与坐标参数，但不要求由不同机器重新计算的数组逐位相同。
- **快速结构派生数据**：此前启用时会重新运行 `prepare`，再比较打包结果。现在客户端核对数据声明和资源绑定，并消费包内经过制包端验证的派生数组；制包端仍做来源等价检查。修复没有删除客户端的文件稳定性、哈希、目录、楼层、坐标绑定、取消和请求当前性检查。

这是能解释“开发者电脑通过、别的电脑拒绝”的具体机制。测试补丁把 S0 模板某个值改动 1 ULP、把快速结构数组换成显然不同的值，并验证客户端不再作机器相关的重算判定；另有错误类型和非有限数值仍在激活前失败的用例。该测试模块名为 `tests.test_original_qt_resource_flow`，本轮 Linux Python 3.12 环境缺 NumPy，无法重跑；PR #162 的合入说明记录了其 Windows 定向运行和资源 Service 实测，但不是其他电脑真机复现。

### 已证实：旧程序可能因同版本更新机制而继续留存

PR [#161](https://github.com/chenhuanh9-a11y/xiaochao-assistant/pull/161) 将产品版本推进到 1.1.8；#162 的提交将 QtIFW 内部组件和策略包版本推进到 `1.1.8.1`，产品显示和 PE 版本仍为 1.1.8。#162 说明指出，QtIFW 原生更新器对同版本 1.1.8 可能不替换内容；内部版本号推进用于确保紧急修复真正进入已安装目录。故只看“星图 1.1.8”不能证明装上了 #162 的修复。由于没有故障电脑的安装器类型及关键程序文件校验值，本轮无法判定它是否仍运行修复前文件。

### 已证实：资源根目录在 1.1.8 变更；旧库未迁移可能表现为“资源消失”

在 #161（变更提交 `06b631f`）中，生产安装的导入库从旧 `%LOCALAPPDATA%/Xingtu/resources` 改为程序目录旁的 `resources`。旧库作为迁移来源单独展示；迁移逻辑先核对文件和库存，再将完整副本发布到新位置，并保留来源。因而旧库尚未迁移可以解释升级后“列表里看不到以前的资源”，但不能单独证明新导入会失败。生产 Setup 的默认位置是用户的 LocalAppData 程序目录，并非默认写入 Program Files；权限问题仍需按故障机器实际安装目录核对，不可先定为根因。

### 已核对但未发现证据：冻结依赖缺失、环境变量回退

`tools/qt-client.spec` 明确收集 NumPy、OpenCV、PySide6 等运行依赖，打包导入代码也在客户端仓库路径中；导入资源根目录由生产安装位置计算，旧 `%LOCALAPPDATA%` 路径只作为迁移来源。源码中未发现导入资源依赖开发者目录或环境变量才能找到的回退路径。此静态检查不能代替对故障电脑实际 Setup、文件清单、杀毒隔离记录和目录权限的检查。

## 调用链与失败影响

「地图资源」页由 `ClientResources.qml` 调用 `ImportedResourceService.importArchive`。后台先检查压缩包、包型和文件名，再执行依赖/上下文准入，随后以受校验的 ZIP 输入保存不可变包版本；基础结构包会继续自动规划和验证激活，最后通过目录事务提交当前启用项。普通文件读取会再次核对稳定性、清单身份、哈希和当前资源上下文。作者显示包走同一导入服务，依赖已启用的结构资源。

保存和启用是两个阶段。因此启用校验失败时，完整的新包版本可能已经保存但尚未启用；这不是半写的包，也不应被说成已启用。激活事务有提交见证与恢复方向，替换目录失败时按事务状态恢复旧目录。现有 `tests.test_imported_resource_activation` 的 9 项事务测试和 `tests.test_imported_resource_packages` 的 27 项包读写/完整性测试均在本轮环境通过。

潜在相邻影响仅限于可用性：基础包未启用时，**地图识别**缺少对应导入资源；作者路线无法供 **自定义图库** 与 **路线显示** 消费。当前没有证据显示身份识别算法、路线贴合、库存完整性或升级迁移发生了错误数据变更。
